Scraping a directory that doesn't want to be scraped

The Google Cloud partner directory has no API, loads its content with JavaScript, paginates behind a button, and gives every partner a different set of sections. Getting all of it into a table is less about scraping than about handling structure that changes row to row.

Tools
Selenium · pandas · openpyxl
Source
cloud.google.com/find-a-partner
Output
8-field structured table

The problem

Google Cloud publishes a directory of consulting partners — who they are, what they specialize in, which products they can advise on, where they operate. It is genuinely useful competitive intelligence, and it is available only as a web page: no API, no export, no downloadable dataset.

Three things make it awkward to extract:

  • The listing is rendered client-side, so fetching the HTML with requests returns a near-empty shell. The page has to be driven by a real browser.
  • Only a slice of partners loads initially. The rest sit behind a load more button that must be clicked repeatedly until it stops appearing.
  • Every partner card has a different shape. One has specializations, expertises, and products; the next has only products and a location. The sections that exist are the only ones rendered, so nothing sits at a fixed position.

Exhausting the pagination

The first job is getting the whole catalogue onto the page. The loop below clicks load more until the button no longer appears — which is how the page signals the end, since there is no page count to read. Both exits are expected outcomes, not errors: NoSuchElementException means the button is gone, TimeoutException means nothing new arrived in time.

The sleep after each click matters. Without it the loop fires requests at whatever rate Selenium can manage, which is both hostile to the host and a good way to get rate-limited mid-run. Polite scraping is also more reliable scraping.

Parsing cards that don't agree on their own structure

This is the actual problem. Within a partner card, each section is a div — but only the sections that partner has. You cannot say "expertises live in div[3]", because for a partner with no specializations, div[3] is something else entirely.

The fix is to walk the divs with a counter, read each section's heading, and only consume the div if the heading matches what you are looking for. If it does not, the field is recorded as missing and the counter stays put — so the next field gets a chance at the same div.

The list-splitting is its own small mess. Google renders these as prose — "Retail, Healthcare and Financial Services" — so turning them into clean lists means handling the comma, the trailing and, and the Oxford-comma variant together.

Assembling the table

With the section reader in place, each card is read field by field in document order, the counter threading through so every field sees the right div. Anything absent comes back as None rather than shifting the remaining fields out of alignment — which is the failure mode that quietly corrupts a scrape and is nearly invisible in the output.

10,824 rows across eight fields. Location is the sparsest column — plenty of partners simply do not publish one, which is a genuine gap in the source rather than a parsing failure, and worth stating plainly before anyone builds a geographic analysis on top of it.

What I would do differently

The positional walk works, but it is coupled to Google's DOM: a layout change reorders the divs and the parse silently drifts. A more durable version would find each section by its heading text directly rather than by index, so the code stops caring what order the sections appear in.

I would also add a row-count assertion against the directory's own displayed total, and log any card where every field came back empty. A scrape that fails loudly is worth far more than one that returns a plausible-looking table with a quarter of the values missing.
